## 세 가지 도구

TypeScript에서 "이 값의 타입을 어떻게 말해줄까"를 표현하는 방법은 크게 셋입니다.

```ts
const a: Config = { ... };            // 타입 annotation
const b = { ... } as Config;          // type assertion
const c = { ... } satisfies Config;   // satisfies
```

겉보기엔 비슷하지만 **좁은 타입을 유지하느냐**에서 갈립니다.

## 문제: annotation은 타입을 넓힌다

```ts
type Colors = Record<string, string>;

const palette: Colors = {
  red: "#ff0000",
  blue: "#0000ff",
};

// palette.red 의 타입 → string (구체적인 "#ff0000" 아님)
```

키가 정말 `string`인지, 또는 `red | blue`인지 알 수 없게 됩니다.

## 해답: satisfies

```ts
const palette = {
  red: "#ff0000",
  blue: "#0000ff",
} satisfies Colors;

// palette.red 의 타입 → "#ff0000" (리터럴 유지)
// 그러면서도 Colors 제약은 검증됨
```

**검증은 하되 타입은 좁게 남긴다** — 이게 핵심입니다.

## 언제 쓸까

- 객체 리터럴이 특정 인터페이스를 만족해야 하는데, 각 필드의 리터럴 타입이 필요할 때.
- 키 목록을 자동 추출해서 유니온 타입으로 쓰고 싶을 때.
- `as const`와 조합해서 불변 + 제약 검증을 동시에 받고 싶을 때.
